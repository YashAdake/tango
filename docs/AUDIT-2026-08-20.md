# Audit — what is actually built, and whether it was built well

A deliberate step back after eight verification passes. Not a summary of commit
messages: I re-read the code, measured coverage, profiled the binary, and looked
for the things a green suite hides.

**Verdict: the core is sound, the edges were not. Four defects found, all fixed.
One was serious enough that it would have shaped the owner's first impression of
the product.**

## 2. Defects found

### D22 · Every command paid 4 seconds for a model most of them never use

**The worst finding, and the most embarrassing.** `tango projects` — which
touches no model, no network, nothing but a JSON file — took **8.5 seconds.**

Profiling put 4.1s of it in `OllamaModel.available()`. The CLI called
`select_model()` eagerly at construction, so every invocation probed for Ollama
whether or not the command could possibly use it. On Windows the probe is slow
precisely when Ollama is absent: `localhost` resolves to `::1` first, and the
IPv6 attempt has to fail before IPv4 is even tried.

This is the architecture's own principle violated at startup. Docs/16 §9 says
deterministic first, model only as fallback — and then the entry point paid the
model cost unconditionally, on the fast path, for nothing.

*Fix:* `LazyLocalModel` — nothing touches the network until the router has
exhausted its rules. The probe is cached and the host is pinned to `127.0.0.1`.

| | before | after |
|---|---|---|
| `tango projects` | 8.51 s | **0.67 s** |
| `tango tools` | ~8.4 s | **0.56 s** |
| unit suite | 151 s | **29 s** |

Against the spec's `p95 < 1.2s` target for the playbook path, the old number was
a 7× miss on the most common commands. Worth stating plainly: **this would have
been the owner's first impression**, and no amount of correctness underneath
survives a tool that feels broken.

### D23 · The CLI — the only surface — had zero tests

197 statements at **0% coverage**, standing between every guarantee underneath
and the person using them. The safety core being well tested does not help if
the surface mis-wires it.

`doctor.py` was also at 0%, which is worse in one specific way: it is the first
thing that runs on the lab laptop, a machine I cannot debug. A doctor that
crashes is a dead end for whoever is holding it.

*Fix:* 20 CLI tests against the real Typer app and a temp store, including that
refusals exit non-zero and are audited, that ambiguity offers options, and a
sweep asserting no CLI output claims an unverified outcome.

### D24 · `system.py` had no error handling at all

Three subprocess calls, zero `try` blocks — while `inspect.py`, written a day
later, has six. Straight drift: I learned the lesson in one adapter and never
went back to the earlier one.

Consequence: `tasklist` timing out under load crashed `tango running` and
`tango stop`. It surfaced as an intermittent test failure under coverage, which
is exactly how this class of bug announces itself — as flakiness, once, easy to
dismiss.

*Fix:* a `ProcessTableUnavailable` exception, and — the part that matters — every
verifier treats it as **`UNVERIFIABLE`, never `REFUTED`**. Reporting "the process
isn't running" because we could not look is the same lie in the opposite
direction. Also `taskkill` no longer implies success: it returns success for a
PID that was already gone, so the verifier decides.

### D25 · The offline distinction was nearly lost

Making the model lazy initially collapsed two different answers into one: *"I
don't have a playbook for that"* and *"I don't have a playbook **and** the model
isn't running."* A test caught it. The second tells the owner what to go and fix;
the first leaves them guessing.

## 3. What holds up

**The verification discipline paid for itself repeatedly.** 25 defects across
eight passes, and the pattern is consistent: unit tests found almost none of
them. Integration found the missing seam. Real execution found the silent step.
The eval found the resolver acting on the word *"the"*. Chaos found the
concurrency claim that was never enforced. This audit found the 8-second startup.

**The honesty layer is genuinely structural, not aspirational.** A tool at R2+
cannot be *constructed* without a verifier. A completion verb cannot be rendered
without `VERIFIED`. Both are enforced at import and in CI, not by discipline.

**Trust boundaries hold under adversarial fixtures.** Eight injection cases pass,
including two-hop payloads and TOCTOU argument swaps — and crucially, reads
still work inside a poisoned task. Containment, not paralysis.

**Degradation is honest everywhere it was checked.** Docker down, model absent,
process table unreadable, verifier broken, store read-only — every path reports
`UNVERIFIABLE` or the real error rather than assuming.

## 4. What I would still change

Ranked by what I would actually do next.

1. **The golden set is mine, not the owner's.** 45/45 measures the router
   against my guesses at how he talks. This is the single largest unknown in the
   project and no amount of further building shrinks it.
2. **Adapters sit at 26–45%.** Docker's is untestable here with the daemon down.
   Worth a fake-subprocess harness so failure paths are exercised without the
   real thing.
3. **`resource_lock` remains an unused table** (docs/17 C4's finer-grained
   proposal). Global serialization is correct but coarser than specced. Fine for
   one user; delete it or build it, do not leave it looking implemented.
4. **`status.py` and `diagnose.py` both probe health and inspect containers.**
   Not duplication yet — different shapes, different outputs — but the second
   time I add a probe to both, it becomes one.
5. **No performance gate.** D22 existed for days because nothing measured
   latency. A CI check on `tango projects` would have caught it the day it
   landed. **Adding one is the highest-value change on this list.**
6. **`import tango.cli` costs 1.16 s** — Typer and Pydantic. Acceptable for a
   CLI, unacceptable for the voice path where the budget is sub-second end to
   end. Phase 2 needs a resident process, not a per-utterance cold start.

---

## 5. The honest assessment

**What is good:** the safety architecture is real and enforced by machinery
rather than intent. The verification discipline finds things. Every capability
built so far works against real state on a real machine.

**What is not:** I optimised correctness and neglected *feel* until an audit
forced the question. An 8.5-second startup is not a small bug on a personal
assistant — it is the difference between a tool someone reaches for and one they
remember they have. The spec has said since day one that latency decides whether
this feels present, and I still let it regress unmeasured for a week.

That is the lesson worth carrying: **the gates measured everything I had decided
to care about, and nothing I had not.** A verification suite is only as honest
as the questions it was built to ask.
